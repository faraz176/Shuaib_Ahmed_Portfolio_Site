EVE-NG Host Capacity Checker

A bounded, read-only Windows workload check built to answer one operational question: does this host have enough memory headroom for the next lab session?

Problem and approach

Measure the constraint before changing the lab.

I wrote a PowerShell sampler that observes the current workload for a configurable 5–120 seconds, reads the existing EVE-NG VM allocation, and records CPU, available RAM, committed memory, disk response, and application memory use. It does not start EVE-NG, close applications, or change system settings.

.\Lab-Check.ps1 -Seconds 30

The tool produces CSV measurements plus JSON and readable text summaries. The report intentionally distinguishes observation from diagnosis: a short sample can expose low headroom, but cannot prove that a configuration change made the computer faster.

Decision rule

Use an explicit reserve, and only under a known VM state.

When EVE-NG is explicitly not running, the script flags limited headroom if minimum available RAM is below the VM's allocation plus a 2 GB planning reserve. With the recorded 4096 MB EVE-NG allocation, that threshold is 6144 MB. It also warns below 1 GB and 2 GB of available host memory.

The EVE-specific rule does not fire for Running or Unknown states because those states cannot support the same before-start decision. The threshold is a conservative planning aid, not an allocation guarantee.

Engineering details

Missing counters fail the run instead of becoming zero.

  • PowerShell performance counters are sampled once per second and checked for missing or invalid values.
  • CPU percentages use process start times to avoid attributing a reused process ID to the wrong process.
  • Disk latency is weighted by transfer count; no-transfer intervals do not become artificial zero-latency results.
  • The report notes when protected or exited processes prevent a complete CPU measurement.
  • Temperature, GPU load, throttling, and network-call quality remain outside the tool's evidence.

Result and limits

A repeatable pre-flight check, not a benchmark.

The eight runs showed how low available memory could become under ordinary workloads and supplied a practical input to later lab-capacity decisions. They do not establish a before-and-after performance improvement. A valid comparison would repeat the same representative lab, applications, call, and sharing settings after changing one variable.
